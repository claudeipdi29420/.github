<p>第三天开始弹人机验证，第七天要求重新登录，第十二天干脆提示环境异常。很多人在这一步做的第一件事是换 IP，换完照旧，于是再换一家，三个月里换了四家服务商，问题一次没解决。养号出状况很少是单点原因，更像一棵树：症状是树冠，往下有若干分支，只有走到真正出问题的那根枝上才有用。这篇按根节点、三条支路和新老号差异，把这棵树画完整。</p>

<h2>一、根节点先分清：是线不纯，还是节奏不对</h2>
<p>树根只有一个判断：问题出在"这条线本身"，还是出在"你怎么用它"。两者表现可以完全一样，处理方式却相反——前者要换资源，后者换资源只会让环境更乱。</p>
<h3>一个五分钟的粗筛</h3>
<p>把同一条线接到一台从未登录过该平台的干净设备上，只做浏览不做登录。若浏览正常、页面不弹任何额外确认，说明线路的基础连通与属性没有明显问题，重点该转向使用方式；若干净设备上也立刻被拦，才轮到怀疑线路。</p>
<h3>粗筛会排除掉大半误判</h3>
<p>实践里，超过一半的"IP 不纯"其实是设备复用、多人共用或节奏突变造成的。先做这一步，能省下大量换服务商的钱和重新适应的时间。</p>

<h2>二、查纯净度的三条支路：ASN、邻址、历史</h2>
<img src="/tp.png" alt="养号场景下住宅 IP 纯净度排查的故障树分支">
<p>如果粗筛指向线路，接着往下走三条支路。三条都过，基本可以认为这条线的属性是干净的；有一条不过，就要看它影响的是哪个环节。</p>
<h3>支路一：ASN 与归属</h3>
<p>查 <code>curl https://ipinfo.io/你的IP/json</code>，看 org 是否为运营商名称、type 是否标为 isp 或 business。再看该 ASN 下有多少地址段被商业转租——这一点查不到精确数据，但可以看同 ASN 是否大量出现在各类代理列表中，方法是把地址与几个公开的 IP 属性查询站交叉核对。</p>
<h3>支路二：相邻地址</h3>
<p>取该地址前后各五个，逐个查归属与在线状态。真家宽一段内往往只有零星几个活跃地址；被批量转租的段会出现整段同属一家、且分属多个国家用户的情况。这条支路最费时间，也最能揭穿"原生"话术。</p>
<h3>支路三：历史使用痕迹</h3>
<p>问服务商这个地址过去三个月是否被分配过、分配给谁、为何回收。正规渠道能给出大致口径，含糊其辞的说明连他们自己也不清楚。回收频繁的地址，往往带着上一任的使用痕迹。</p>

<h2>三、出口稳定性的支路：抖动、切换与共享度</h2>
<p>纯净解决的是"像不像"，稳定解决的是"像不像同一个人"。一条地址再干净，若三天两头换出口，账号侧看到的仍是漂移。</p>
<h3>抖动看的是波动幅度</h3>
<p>连续五天在同一时段跑 <code>mtr -rwc 100 目标域名</code>，记录末段丢包与平均时延。时延波动超过一倍、或丢包在 2% 以上反复出现，会直接影响长连接的稳定性，表现为回复中断、上传失败。</p>
<h3>切换频率要数出来</h3>
<p>一个月内这条线的出口地址变了几次？超过一次就该警惕。有的方案表面是静态，实际在上游做 NAT 池轮换，你从控制面板看不出来，只能靠每天记录出口 IP 对比。</p>
<p>这条线上还挂着几个用户、能否保证不与其他项目混用、超出带宽时会不会被限速，这三个问题里只要有一个答不清，就按共享对待，别按独享规划。共享度是所有指标里最不透明的一项，也是最容易在两个月后集中爆发的一项。</p>

<h2>四、操作节奏的支路：新号前三十天的时间轴</h2>
<p>设备和线路都过关，剩下的就是节奏。新号对节奏最敏感，因为平台没有历史行为可参考，任何突兀的动作都会被放大。</p>
<h3>第一周只做低频动作</h3>
<p>每天登录一到两次，每次十分钟以内，做最基础的对话，不改资料、不换设备、不连续追问长文。目的是让账号侧积累"稳定、低频、可预期"的记录。</p>
<h3>第二到第四周逐步加量</h3>
<p>每周增加一档使用强度，同时保持时段相对固定。避免出现"前一天零使用、后一天连续四小时"的断崖式变化，这种模式在任何账号上都不自然。</p>
<p>不是要"演得像"，而是别在短时间内同时改变太多东西。换设备、换出口、改资料、加订阅，四件事分四周做，出问题才知道是哪一件引起的。这条原则比任何节奏模板都管用，因为每个人的使用强度本来就不一样，硬套模板反而会让曲线更突兀。</p>

<h2>五、老号出问题的树，起点完全不同</h2>
<p>老号有历史记录，所以判断逻辑要反过来：先看"最近变了什么"，而不是"这条线纯不纯"。一个用了半年的号突然异常，八成是某个变量被动过。</p>
<h3>先查变更清单</h3>
<p>最近两周有没有换过出口、换过设备、换过浏览器版本、换过人使用、改过密码或邮箱。五项里找到一项，基本就锁定了范围。</p>
<p>再看线路侧有没有被动调整。服务商侧的上游变更、地址段迁移、带宽限速，都会在你不知情的情况下改变出口。这就是为什么每天记一次出口 IP 很有必要——它是唯一能证明"我没动、是它动了"的证据。</p>

<h2>六、画成一张值班也能用的判定表</h2>
<p>树画完要能落地。把最常见的四种症状和对应分支写成一张表，值班的人不需要理解原理，照着走也能得到一致结论。</p>
<h3>四条主路径</h3>
<p>打不开、要验证、能登录但功能受限、用着用着中断。每条路径的前三步动作固定，第四步才允许判断是否换线。前三步不许跳，跳了就会回到"换 IP 解决一切"的老路。</p>
<h3>结论要写成动作</h3>
<p>不要写"检查网络"，要写"运行 mtr，若第 9 跳后丢包超过 2%，切备用线并记录时间"。可执行的句子才能被重复执行，也才能在交接时不出偏差。</p>

<h2>常见问答</h2>
<h3>纯净度检测一定要做邻址排查吗？</h3>
<p>答：预算有限时可以只做 ASN 与归属核对，能挡掉大部分明显不是住宅段的地址。但若你打算长期使用同一条线，邻址排查值得做一次，它是判断"整段是否被批量转租"最直接的方法。</p>
<h3>新号前几天完全不用，会不会更好？</h3>
<p>答：不建议。长期零活动的账号同样不自然，且平台对"注册后长期静默再突然高频使用"的模式更敏感。保持低频但稳定的使用，比放着不动更接近真实用户。</p>
<h3>换线之后要养多久才能恢复？</h3>
<p>答：没有固定周期，取决于账号历史与变更幅度。可观察的信号是验证频次逐步下降、页面提示消失。这段时间内不要再叠加其他变更，否则无法归因。</p>
<h3>多人共用一个账号，怎么降低摩擦？</h3>
<p>答：技术上可以固定同一出口与同一设备，但多人多地共用在多数平台的服务条款里本身就不被鼓励。建议按平台规则为每位使用者配置独立账号，而不是靠技术手段掩盖共用事实。</p>
